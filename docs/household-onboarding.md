# 配偶者のログインを追加する

妻の人物マスタが存在しても、妻のログインが使えるとは限らない。2026-09-10時点でメールアドレスは未確認。架空Authによる共有テストを本番招待完了と扱わない。

初回の本人確認・表示名設定は [本人と支払元の表示](member-profiles.md) を参照。招待先は従来どおり固定のpartner人物IDへ管理者が紐づける。nicknameで人物を探したり、新しい人物を作り直したりしない。初回確認は本人が画面で行い、招待作業から確認済みへ更新しない。

## 作業の順序

1. `docs/shared-database.md`、基盤の `AGENTS.md` / `docs/status.md` を読む。対象は `fpptihhtyhehpjvmtuqt` のfamfiだけ。
2. 本人から妻の実際のログイン用メールを確認する。管理画面、同名ユーザー、チャットに過去貼られたOTPから推測しない。
3. 共有Authの既存ユーザーを完全一致で確認する。既存なら再利用する。未登録なら公式Auth管理機能で招待する。SQLで `auth.users` を作らない。一般新規登録、共有SMTP、他アプリのredirect URLを変更しない。
4. 標準SMTPの配信制限を確認する。宛先がOrganization外ならカスタムSMTPが必要になり得る。配信できない状態で再送を繰り返さず、費用/ドメイン/共有影響を認識合わせする。
5. 確認済みAuth UUIDについて、停止・削除・既存famfi/他アプリの所属を照合する。既存の家計IDと `parties.system_key='partner'` の人物IDを管理接続で解決する。人物名だけで対応付けない。
6. 基盤の管理用トランザクションと共有advisory lockで、妻の `famfi.memberships` と `household_members(user_id,ledger_id,party_id)` を追加する。別の家計に既に所属していたら自動移動・上書きをしない。**妻へ `provision_household` を呼ばない。** 夫の家計へ追加するので新規家計・カテゴリ・支払元を複製しない。
7. Vercel Productionの `FAMFI_ALLOWED_EMAIL` に既存アドレスを維持してカンマ区切りで追加し、再デプロイする。これはコード送信先の制限で、家計の権限台帳の代わりではない。Previewへ本番DB設定をコピーしない。
8. 本人がメールコードを入力し、妻としてログインした画面で同じ支出が見えること、新規の購入者が自分（妻）になることを確認する。招待直後は `/login?mode=invite`、通常は `/login`。OTPをログ・Git・チャットに残さない。
9. 実データへのテスト書込みは対象を明示して同意を得る。別家計・未参加ユーザー・他スキーマ拒否も確認し、基盤の運用記録へ日時・対象範囲・結果を記録する。メールや秘密情報を公開文書に記載しない。

## 権限と復旧

- 夫婦は同じ家計を編集できるが、アプリから参加者を追加・変更する権限は持たない。
- 家族/自分/その他は入力用の固定選択肢。自分は保存時には実在の人物IDであり、閲覧者によって過去の購入者が変わらない。
- `memberships.active=false` にすると、その本人の家計アクセスを拒否する。家計IDとして使っている元のowner membership行や共有のAuthユーザーは削除しない。夫を停止しても妻の有効な参加は別に判断する。
- v4バックアップは家計データと人物IDを含むが、共有Auth・ログイン資格情報・他メンバーのAuth対応表は含まない。Authと参加者の復旧は別の管理手順で本人確認して行う。復旧確認スクリプトの架空Auth行を本番へ流用しない。

依頼例: 「妻のログインを追加したい。メールは○○です。既存家計の妻の人物に紐付け、他アプリの権限や共有Auth設定を変えずに進めてください。」
