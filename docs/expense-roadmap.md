# 支出管理の機能一覧と今後の方針

確認日: 2026-09-09。本人要望を記録した開発方針であり、下記の未実装機能を公開したという意味ではない。

## 最初のゴールは維持する

「まず支出を登録して管理を始める」が最優先。ただし最低限の入力画面を作って終わりではなく、スマホで無理なく入力を続けられることを判断基準にする。
今回の追加要望は、カテゴリマスタの管理・色変更、誰が使ったか、共用カードか個人の立替かの記録、後日の精算。入力開始をこれらすべての完成まで待たせない。

## 本番と未実装の区別

| 機能 | 本番MVPの状態 | 旧試作・次の対応 |
| --- | --- | --- |
| 支出の登録・編集・削除 | 実装済み | 金額、日付/年月、カテゴリ、内容、メモを保存 |
| 月別集計・カテゴリ別内訳・CSV出力 | 実装済み | 支払元別、利用者別、精算状態別の集計は未実装 |
| カテゴリの色表示 | 実装済み | 選択肢・選択後・内訳で表示。本人による色変更は未実装 |
| カテゴリマスタ管理 | 未実装 | 旧試作に名称・色・子カテゴリの編集あり。本番の追加/編集/並べ替え/使用停止を作る |
| 親子カテゴリ | 未実装 | 旧試作の二段構成を再設計。親のみでの登録も残す |
| 人の管理、支払者、誰のための支出か | 未実装 | 旧試作に `Person`、`paidBy`、`beneficiaries` あり。実際に使った人との違いを明確にする |
| 支払方法・支払元マスタ | 未実装 | 旧試作は現金/クレジットカード等の文字列。共用カードと個人カードの区別や資金の出所まではない |
| 立替の記録・未精算一覧・精算履歴 | 未実装 | 本番にも旧試作にも精算の一連の処理はない。支払方法の選択だけでは代用できない |
| 連続入力・複製・テンプレート | 未実装 | よく使う設定の再利用、保存して次へ、過去記録の複製を候補にする |
| 文字検索・詳細な絞り込み | 未実装 | 現在は月とカテゴリのみ。内容/メモ検索、人物・支払元・未精算による絞り込みを追加候補にする |
| 固定費・定期支出 | 未実装 | 旧試作に定額/変動額・月ごとの確定あり。実記録の重複を防いで本番化する |
| 収入・予算・貯蓄目標・月締め・詳細分析 | 未実装 | 一部に試作・仮表示あり。日々の支出入力と立替把握の後に対応 |
| 家族の複数アカウントによる共同編集 | 未実装 | 人物を記録することと、他アカウントへ閲覧/編集権限を与えることは別 |
| CSV取込・カード明細照合・レシート画像/OCR | 未実装 | 今後の候補。CSV出力があることを取込・自動連携対応と説明しない |
| 返品・返金・精算済み記録の訂正履歴 | 未実装 | 元の支出との関連と未精算額の訂正を設計する。負の支出を場当たり的に追加しない |

## 人とお金の区別

実装時の概念整理。列・テーブルの確定設計や移行SQLではない。

| 情報 | 意味 |
| --- | --- |
| 記録者 | アプリに入力・変更した認証済みアカウント。支出した人とは限らない |
| 利用者 | 買物やサービスを実際に利用した人。本人以外も記録できる想定 |
| 誰のための支出か | 本人、特定の家族、家族全体など。利用者や支払者と一致するとは限らない |
| 支払方法・支払元 | 現金/カード/振込等と、具体的な個人の財布・個人カード・共用カード・共用口座 |
| 資金の負担元・立替者 | 個人が先に出したのか、共用資金から出たのか。カード名義だけで判断しない |
| 精算先と負担額 | 最終的に誰/どの共用資金がいくら負担し、誰へいくら返すのか |

- 現在の `Expense.userId` はデータの所有・アクセス範囲を制御するもの。利用者・支払者・立替者へ自動転用しない。
- 人物マスタに家族を追加しても、共有Authアカウントや他アプリの利用許可を自動作成しない。最初は本人一人が家族分も記録できる形を候補にする。
- 個人カードでも家庭用なら立替になり得る。共用カードでも個人利用分の精算が必要になり得る。「カード/現金」だけで精算要否を決めない。
- 既存支出の人物・支払元は未設定として保持し、本人や共用扱いを推測で埋めない。後から補足できるようにする。
- カードは識別用の名称で管理し、カード番号・セキュリティコード・金融機関のログイン情報は通常のマスタに保存しない。

## 立替と精算の要件

例: 家庭用の日用品3,000円を本人が個人カードで立替。後日、共用口座から本人へ3,000円を返す。

- 支出として数えるのは購入時の3,000円だけ。返したお金は元の立替に関連付く精算記録であり、新たな支出や収入として二重計上しない。
- カード利用時の支出と、後日の口座引落しも区別する。将来の明細取込では既存支出との重複を防ぐ。
- 未精算/一部精算/精算済みと残額を一覧で確認できる。誰から誰へ、いつ、いくら精算したかを履歴として保持する。
- 複数の立替の一括精算と一部精算を扱うなら、対象支出への配分を保持し、二重精算・過払い・同時操作の競合を防ぐ。
- 精算記録の訂正・取消では残額を再計算する。精算済みの支出金額や負担先を変える場合も、関連する精算を無視して変更しない。
- 月のみの支出も精算対象にできる。支出の年月と実際の精算日は別の情報として扱う。
- 「後で確認が必要」と「精算不要」を区別する。負担ルールが未確定なのに自動で精算済みや折半にしない。
- 最初は人が実際に返金した結果を記録する機能とする。アプリからの自動送金・カード決済は含めない。
- 上記は段階的に実装し、対応していない混在負担や一部精算を、対応済みとしてUIで受け付けない。

## 実装の優先順位

1. 継続して使える入力: 実機の不具合修正、データ保持、バックアップ運用。カテゴリ・支払元が増えても入力が重くならないことを確認する。
2. カテゴリマスタ: 名称/色変更・追加・並べ替え・使用停止・親子カテゴリ。入力中に管理画面へ移っても入力内容を失わず戻れるようにする。既存カテゴリの所有範囲と編集権限を先に設計する。
3. 人物・支払元・立替記録: よく使う人と支払元を少ない操作で指定し、必要なものだけ立替/要確認にする。家族のアカウント共有完成を前提にしない。後で精算対象を抽出できる構造にする。
4. 精算: 未精算一覧、相手別の残額、精算記録、関連支出への配分と訂正。日々の立替が増える前に優先し、固定費や分析画面より先に扱う。
5. 入力支援と定期支出: 複製、テンプレート、検索、固定費。小さな入力改善は各段階で取り込み、すべてをこの段階まで待たせない。
6. その他: 家族の共同編集、収入、予算、取込/明細照合、レシート、詳細分析。レシピ・家事・予定は別の後続機能。

これは現時点の推奨順。実際の利用で立替が多ければ、人物・支払元と立替記録をカテゴリの高度な管理より先に進める。費用負担のルールや家族への権限付与は実装時に認識合わせし、推測で確定しない。

## 使いやすさの受け入れ条件

- 基本の金額・日付/年月・カテゴリで登録でき、補足項目が未設定でも入力を止めない。精算実行に必要な情報だけ、その時点で求める。
- よく使う設定を既定値/候補として再利用する場合は、選択内容が見えて簡単に変えられるようにする。利用者や負担額を見えないところで決めない。
- 詳細欄は必要なときだけ開く。共用カード等は登録済みの支払元から選び、毎回同じ情報を入力させない。
- 保存失敗時・競合時は入力を保持する。閉じる/移動での入力破棄を防ぐ確認や下書きの扱いを追加候補にする。金額・メモを安易にブラウザへ平文で永続保存しない。
- 編集・複製・連続入力から履歴へ戻る際、月・絞り込み・スクロール位置を不必要に失わない。
- スマホの縦横・短い画面・キーボード表示でも入力欄、プルダウン、通知、保存ボタンが操作を妨げない。色に加えて名称・状態表示を使う。
- 必要な人物・支払元・精算情報は詳細/一覧/絞り込み/CSV/バックアップに一貫して反映する。UIに欄だけ追加して完了としない。
- 使用済みマスタは原則使用停止にし、過去の支出や精算との関連を失わせない。
- DBや権限の実装は共有DBのルールに従う。旧試作モデルを一括適用せず、正本の基盤リポジトリに移行SQLと拒否テストを登録する。
