## 管理するもの

- 銀行口座からの入金・出金を、購入した支出とは別の `cash_movements` に保存する。残高や資産額は管理しない。
- カードの引落日と購入日・利用月は異なる。引落額から支出・まとめ記録・精算・定期実績を自動生成しない。支出合計、カレンダー、月の確認事項には加算しない。
- 関係者は初期値も取込時も「不明」。ログインした人や振込名義から夫・妻、受益者、カード名義を推測しない。
- 支払元マスタの銀行口座を使用する。共通口座の資金所有者は共用資金。カード名義とは独立し、既存の家族カードや支出の初期値を変更しない。
- 手入力では口座・日付・符号付き金額・内容が必須。種類は用途不明/カード引落/口座引落/資金移動/家計への入金/手当・給付金/利息/返金/手数料。方向が決まる種類には入出金の制約を設ける。
- 直接負担の支出は架空の銀行入金に変換しない。銀行からの振込を立替精算済みと自動判断しない。

## 画面と保存

スマホはメニューの「入出金」、PCは同名タブ。月/全期間・方向・種類・口座・内容/メモの検索と、その条件に一致する合計・CSVに対応する。初期表示は合計と履歴を優先し、条件指定は折りたたむ。中央の+は従来どおり支出登録。

手入力は全業務項目を訂正できる。取込明細の口座・日付・金額は原本の事実なので変更不可とし、内容・種類・関係者・メモは後で補足できる。同時更新はversion競合で拒否し、入力を保ったまま最新を読み直せる。

削除は論理削除。通常の画面・集計・CSVには出さないが、取込識別値と変更履歴を残す。同じ明細を再取込しても復活させず、後から補足した内容も上書きしない。使用済み口座の資金所有者・支払方法の変更は拒否し、名称変更・使用停止を使う。

アクセスは既存のサーバー検証済みAuth・家計参加・`withUserDb`・RLSに従う。本人と妻は同じ家計内だけを共有し、他家計・他schema・未認証は拒否。INSERTは業務列限定、物理DELETEは禁止。

## CSV取込

現段階は管理者のローカルCLIのみ。画面のアップロード、楽天への自動接続、カード別内訳、購入明細/精算との照合は未実装。

- CP932/Shift-JISまたはUTF-8、見出し4列の楽天銀行CSVを検証する。日付・金額・並び順・連続する取引残高の整合を確認し、不一致・同一行重複は停止する。
- 残高は検証と明細識別用ハッシュの計算にだけ使い、DBや出力へ保存しない。名義、相手口座番号、管理番号を含む生の摘要も保存しない。
- 確実な銀行摘要だけをカード引落等へ分類し、その他は用途不明とする。分類は購入カテゴリや精算要否を意味しない。
- 重複判定は家計・取込先口座・原本の行ハッシュ。期間が重なるCSVにも対応する。同じファイル内の重複は原本確認が必要なので黙って除外しない。
- 口座IDを誤って変えると別口座として扱われる。CSV自体から口座名義を確定できないため、初回に取込先を確認し、以後も同じ口座IDを使う。
- 生CSVはGit/ログ/テストfixture/Previewへコピーしない。検証用DBには架空CSVだけを使う。

原本だけの読取検査（DBに接続しない）:

```sh
node --import tsx scripts/import-rakuten-bank.mjs --file <原本CSVのパス>
```

DBへ進める前に、管理者が対象project ref、有効な家計参加、メール確認済み本人Auth UUID、銀行口座マスタの所有者とIDを照合する。Authやmembershipを作り直さない。口座を追加する場合も既存マスタAPI相当の検証と専用runtimeを使い、他の支払元を変更しない。

```sh
NODE_ENV=production FAMFI_DB_SCHEMA=famfi node --import tsx scripts/import-rakuten-bank.mjs \
  --file <原本CSVのパス> --actor <確認済みAuth-UUID> --source <確認済み銀行口座UUID>
```

dry-runの新規/取込済み/削除済み件数と原本SHA-256を確認後、同じコマンドに `--apply --allow-production-import --expected-sha256 <確認値>` を追加する。URLはGit外 `.private/database-url` を読み、通常の `famfi_app` と厳密なTLSを使う。実データ取込はProductionのみ。

実行前後にv8暗号化backup・独立DBへの復元・既存全項目の保持を検証する。10件単位の家計ロック付きtransactionで登録するため、途中障害では一部が登録済みになり得る。同じ原本/口座でdry-runをやり直せば、完了済みを上書きせず再開できる。照合中の並行変更を避けるため、家族の入力がない時間帯に実行する。失敗時に自動削除・巻き戻しはしない。
